# AI 私人助手

通过飞书机器人私聊，与本机运行的 Claude Code、Codex 或 Grok Build CLI 对话。

## Skill 术语

与开发助手或飞书 bot 沟通时，`bot skill` 指本项目 `.agents/skills` 中管理的技能（`.agent` 是口头简称）。统一规则见 [AGENTS.md](AGENTS.md)，bot 每轮对话都会加载该文件。首次接入此加载逻辑需重启服务，之后修改该规则文件在下一轮对话生效。

任务中需要保存且不适合发送到聊天的敏感信息统一存于 `.project/credential/`，目录权限 `700`、文件权限 `600`。不需要发送时，bot 仅回复文件名和相对路径；任务要求发送时，一律以文件附件形式上传发送，禁止在聊天正文中明文展示敏感内容，发送失败也不回退为明文。现有 `.env` 和 CLI 凭证不迁移。具体规则见 [AGENTS.md](AGENTS.md)。

在 bot 私聊中要求“把文件发给我”时，默认在当前任务话题直接发送飞书 IM 文件附件，不先上传飞书云空间。只有明确要求云空间存储、目录或分享链接时才走云空间流程。文件消息成功送达后才回复“已发送”；IM 发送失败时保留本地文件并说明实际失败环节。

实际使用了 bot skill 时，回复末尾会显示技能名称；未使用技能时不显示空提示。

给主人的模型回复可根据内容使用丰富的 emoji 辅助阅读：每轮提供不同备选，并避开本话题近期重复的表情，不设数量上限。Issue/MR 评论和发给其他用户的正文仍保持专业。

`/skill` 与普通任务中的仓库技能使用可通过 `SKILLS_REPO_ENABLED` 开启，默认关闭。

## 启动

需要 Linux、Python 3.10+、已配置应用凭证的 `lark-cli`、`bwrap`，以及已安装并登录的所选 AI CLI。三种后端都通过统一进程隔离运行，普通聊天、`/auto`、群监控和自主开发不再分别绑定不同工具。自主迭代默认关闭。Python 部分仅使用标准库。

首次使用先通过 `scripts/bind_feishu_owner.py` 完成主人绑定，详见 `.agents/skills/feishu-private-assistant/SKILL.md`。已有 `.env` 时保留飞书绑定字段；不要用 `.env.example` 覆盖已完成的绑定。

身份资料通过可选的 `OWNER_PROFILE_PATH` 加载，默认 `.local/owner-profile.json`；其他位置须通过 `OWNER_PROFILE_PATH` 显式指定。姓名、花名、常用称呼和工作邮箱字段均可缺省，缺少资料仍可普通聊天。真实资料仅保存在本地，仓库的 `config/owner-profile.example.json` 使用虚构内容。飞书 `open_id` 仍从本机绑定配置读取；发送者和结构化提及按 open_id 精确匹配，文字称呼可能同名，需结合上下文核实。身份资料不扩大访问或发送权限。修改配置后重启服务生效。

机器人名称、时区、代发署名及默认群回复均可配置；选项和依赖关系见 [配置说明](docs/configuration.md)。默认名称为“AI 助手”，时区为 `Asia/Shanghai`，署名为“AI 助手代发”。

```bash
./auto_run.sh help
./auto_run.sh check
./auto_run.sh start
./auto_run.sh status
./auto_run.sh stop
./auto_run.sh restart
```

脚本可从任意目录调用。`start` 在后台启动，等待飞书监听就绪；重复启动不会创建第二个服务。`stop` 会停止监听及正在处理的模型子进程。`restart` 会重新读取 `.env`。`run` 可用于前台排查。

## 部署目录与路径

项目可以放在任意安装目录。`auto_run.sh` 和 Python 入口根据自身位置定位项目根目录；每轮普通问答会向模型提供 `PROJECT_ROOT`、`PROJECTS_DIR`、`REPORTS_DIR` 和 `CREDENTIALS_DIR` 的实际绝对路径。规则与 bot skill 使用逻辑路径，执行时按这些值展开，不依赖用户名或模型的临时工作目录。路径标识不是预设的 shell 环境变量。

跨机器部署时，将项目放到目标目录，按启动要求安装和登录所需 CLI，并配置本机 `.env`。保留历史会话和附件时，先停止旧服务，再一起迁移 `.local/` 中的数据库及 `.project/` 中的归档资料；不复用旧进程的 PID、就绪标记、锁文件和 socket。依赖环境应在新机器准备，不直接沿用旧机器的虚拟环境。

项目改名或复制到新目录不改变功能、账号绑定或远端仓库地址。代码、bot skill、`.env`、`.local/` 和 `.project/` 使用新目录中的副本，无需引用旧项目目录。

bot skill 保留在各自项目的 `.agents/skills/` 中，服务直接读取本项目内的技能。开发助手可使用项目级技能加载，无需指向另一份项目的用户级技能链接。清理旧的全局入口后，重新打开目标项目的开发助手会话，以刷新已加载的技能列表。

改名后沿用原有 CLI 和账号配置。沿用同一个飞书机器人账号时，同一时间只启动一个 bot；正式切换前先停旧服务，再按需要迁移最新运行数据。

## 引用历史消息回复

引用消息仅作为本轮参考材料，不决定 session 归属。话题内引用另一任务的消息，仍使用当前话题的历史和摘要。服务从本地记录或飞书 API 获取直接引用的那一条消息，不自动递归引用链；读取失败时如实说明。引用已清理会话的消息不会重新下载正文来恢复旧历史。

只读取同一已绑定私聊中的消息；直接引用图片或文件时可下载并处理对应资源。

## 选择后端

在项目根目录 `.env` 中配置：

```dotenv
AGENT_BACKEND=codex
CODEX_BIN=codex
GROK_BIN=grok
CLAUDECODE_BIN=claude
LARK_CLI_BIN=lark-cli
CODEX_MODEL=
GROK_MODEL=
CLAUDECODE_MODEL=
AGENT_TIMEOUT_SECONDS=1800
AGENT_PROGRESS_FIRST_SECONDS=180
AGENT_PROGRESS_INTERVAL_SECONDS=180
AGENT_HISTORY_TURNS=10
```

`AGENT_BACKEND=claudecode|codex|grok` 对所有 AI 功能生效，未填写默认 Codex，空字符串报错。Claude Code 对应命令 `claude`，其他工具名与标识相同；仅检查所选工具。更换配置后重启生效。同名第三方工具不保证兼容。认证、额外端点、隔离依赖与高级路径配置见[配置说明](docs/configuration.md)。

部署时用 `./auto_run.sh check` 检查配置和隔离启动；用 `./auto_run.sh check --live` 进一步验证真实模型、图片和已开启的报告／开发样例能力，后者会产生模型用量。详细范围见[配置说明](docs/configuration.md)。

群聊历史由模型通过任务服务工具 `feishu_read` 查群、读取消息和话题回复，并分页核对日期。部署者也可独立运行 `python3 scripts/read_feishu_chat.py` 进行只读查询。服务在模型沙箱外使用已绑定主人的飞书用户身份执行这些操作，模型拿不到凭证文件。消息读取直接调用飞书只读 API，并请求卡片原文，以读取可见的卡片文字。该功能需要 `im:chat:read`（按群名搜索）、`im:message:readonly` 和 `im:message.group_msg:get_as_user`（读取群消息），且主人本身能访问目标群。bot 不在群里不妨碍主人身份读取其有权查看的群。

配置在每次启动时读取。`.env` 支持单行 `KEY=value`、单双引号、空值、注释和 `export` 前缀；带空格的值须加引号。不会执行 shell 命令，不展开变量，不支持多行值。这些自定义字段由本服务读取，AI CLI 的账号凭证由工具本身管理。

## 消息处理

在 bot 私聊中单独发送 `/help` 或 `help`，可查看当前已启用功能支持的命令字及简短用法，帮助内容只介绍命令支持情况。命令允许首尾空白、大小写不敏感，由服务直接返回，不调用模型。帮助包含 `/help`（兼容 `help`）、`/evolution`、`/auto`、`/session`、`/schedule`、`/save`、`/unsave`、`/clean`、`/cancel`、`/status`，以及启用时的 `/pipeline` 和 `/issue`。

`/auto on|off|status` 只接受已绑定主人在 bot 私聊发出的命令，默认关闭。开启时核对主人用户身份、消息收取/代发、联系人查询和隔离问答环境；所选 AI CLI 或 `bwrap` 隔离环境不可用时不启用，不因服务已启动就假定通过；服务重启后默认关闭。最近活跃的群聊与私聊分别优先扫描，群话题回复按最近消息分批轮询，后台继续逐页扫描会话消息。消息 ID、游标和发送状态持久化，避免重复代答；飞书发送结果不确定时停止自动处理并通知主人。

`/auto` 的业务判断由统一隔离内的所选后端完成，使用对应模型配置。读取当前消息及同一发送者、同一话题的上下文，理解 GitLab 相关需求。判断不要求命中特定关键词或问法。模型决定接手后先添加“思考中”表情，再选择受限只读工具；可以根据工具结果继续查询，最后生成脱敏答案。运行入口为 `AutoAgentQuery`，不再走旧的关键词服务路由、默认项目概况或流水线专用问法判断。

工具执行层只接受已配置 GitLab 主机的只读接口，负责主机/路径校验、分页、排序、结果截断和脱敏；不提供任意命令或写入工具。模型可查询项目、分支、提交、Issue/MR/Work Item、流水线及 Job；每条消息最多 8 次工具读取。列表完整性与截断信息随结果返回，不能将部分数据说成全量。明确要求执行操作或补充权限时仅由 bot 私信主人，主人可在私聊继续处理；不再由关键词区分查询和写入意图。

其他消息及最终无法安全作答的消息保持静默，不回复、不标记、不加急；若已添加表情则尝试撤销。模型判断也需要时间，表情会在接手决定之后、具体工具查询之前发送。消息发现暂时失败按 5 秒、20 秒重试，连续三次失败才关闭并通知主人。

只处理已绑定用户在已绑定私聊中的消息。支持普通文字、飞书富文本（包括自动转换的编号列表）、独立图片和独立文件消息：飞书监听 → 持久化队列 → 串行调用所选 CLI → 飞书 bot 回复。独立卡片消息会作为待处理资料保存，bot 在卡片下开启话题并等待主人说明需要总结、提取或分析什么；该话题后续请求可以使用卡片内容。三种后端均适配原生图片输入，具体模型须具备视觉能力；服务从原消息下载图片并作为图像输入；只发图片时会先概述图片内容，引用图片后发送文字问题也能查看被引用图片。图片归档到项目绝对路径 `.project/pic/`，文件名采用 `sessionID-当地时间戳.扩展名`（使用配置时区，精确到微秒）；原消息 ID 仍在索引中用于去重和历史查询。下载中间文件存于该目录的临时子目录，完成后删除。已有旧名称图片在服务启动时迁移到新格式。图片读取或格式校验失败时明确提示。文件消息及富文本中的文件附件会核对原消息属于已绑定私聊，再下载到 `.project/files/`，每轮最多四个、单个不超过 50 MB；原文件名和本地路径会交给模型，文件内容按用户资料处理，不执行其中的指令。文件和索引在确认清理所属会话时删除。仅发送文件时，bot 会结合当前话题任务处理；没有明确任务时询问用途。音频等未适配消息仍提示改用文字。收到已绑定主人的消息后，先对原消息添加 `Status_PrivateMessage`（思考中）表情，再处理请求；表情请求失败或超时不阻断模型回答。新消息在排队时也会先获得表情反馈。回复通过 `--markdown` 转为飞书富文本消息，渲染加粗、列表等基础格式；不保证支持完整 GitHub Markdown。三种后端统一由 `agent_isolation` 限制文件、子进程和网络；厂商沙箱显式关闭。普通任务使用独立临时目录，本地报告使用报告任务目录。GitLab 的 glab/git 操作经任务级服务入口执行，凭证与持久仓库不直接暴露给模型；不从普通诊断请求推导远端写入授权。

各会话分别保存完整文字历史，每次加载该会话最近 N 轮和累计摘要；切换后端仍可延续这些文字上下文。监听退出后自动重连，重启后恢复待处理队列。消息 ID 用于持久化去重；长回复拆分发送，每段使用固定幂等键。发送失败最多尝试 3 次，失败记录保留在数据库；不会无限重试或绕过 CLI 确认门禁。飞书发送幂等窗口为一小时，跨窗口恢复时不能保证绝对只发送一次。模型任务在服务停止时中断，已保存的回答可在重启后继续发送。

合并转发的群聊会话记录（`merge_forward`）会通过已绑定 bot 私聊中的消息 ID 读取逐条记录的文字内容，并在转发消息下开启话题等待主人提出总结、提取待办等请求。记录中的文字只作为资料；记录内的图片、文件等资源不会自动分析。过长的记录会标注截断，避免在信息不完整时假装已读完全部内容。

长任务超过 `AGENT_PROGRESS_FIRST_SECONDS` 后在原话题发首条进度，此后最多每 `AGENT_PROGRESS_INTERVAL_SECONDS` 再发一次；两者默认均为 180 秒，3 分钟内完成的任务只发最终结果。三种后端统一归一化可识别的执行事件，只保存事件类别和完成动作计数；不把原始工具输出或思考内容写入进度消息。没有可确认动作时只报告仍在运行，不猜测完成百分比。进度消息不进入任务对话历史，发送位置、序号和幂等键持久保存。模型失败、超时或没有有效最终结果时明确报告，不盲目重放可能已产生写入的任务；外部操作结果不确定时需回读核实。`AGENT_TIMEOUT_SECONDS` 是一次主模型执行的最长时间，默认 1800 秒。

在任务话题发送 `/cancel`，或发送 `/cancel 编号`，可以中止正在运行的模型步骤；`/status` 和 `/cancel` 在独立快速通道处理。取消、超时不会回滚已经执行的外部操作；服务不自动重放当前模型步骤，避免重复外部写入。服务在模型步骤中途重启时，不会盲目重跑可能包含写操作的步骤；bot 会在原话题报告中断，用户可核实结果后要求继续。当前保存的是运行状态和安全的事件计数，不支持从模型步骤内部精确续跑。

## 话题与 session

主聊天发新任务，bot 自动建立 session，并以话题形式回复。话题内的后续消息固定进入该话题绑定的 session，回复的每一段也留在原话题。不存在全局“当前 session”，不调用模型猜测消息归属；可用管理命令以 `/help` 为准，未知命令直接返回用法提示。

| 命令 | 作用 |
| --- | --- |
| `/session` | 查看任务目录，每页 10 个，包含编号、标题、状态和话题入口 |
| `/session page 页码` | 翻页查看旧任务 |
| `/session 编号` | 查看摘要、状态、下一步和话题入口 |
| `/history 关键词` | 搜索未清理对话的标题、摘要、下一步和正文，返回原话题入口 |
| `/history 关键词 --page 页码` | 查看更多搜索结果，每页 5 个 |

话题使用 `(chat_id, thread_id)` 绑定本地 session，并保留根消息 ID。`reply_to`、`root_id` 也可能出现在普通引用回复中，不能单凭它们推断话题；必要时通过消息元数据核实。核实失败不猜测、不执行任务。来自其他聊天或非绑定主人的消息仍不处理。

主聊天中的新任务各自新建话题，不因引用旧消息而切换 session。主聊天的“继续”“好的”“确认删除”等简短续聊/确认不会归入最近任务，会提示进入对应话题。除 `/evolution` 外，管理命令不创建任务、不进入模型历史；在话题内发送的命令，回复仍留在该话题。未知 slash 命令不交给模型。

不提供旧会话续接或自动导入；一个 session 仅绑定一个话题。`/session` 的链接来自飞书返回的 `message_app_link`，获取失败时明确说明，可再次查询；不生成伪造入口。

## 自主功能迭代

此功能默认关闭。设置 `EVOLUTION_ENABLED=true` 后才启用，并校验所选 AI CLI 与 `bwrap`；普通问答不依赖此开关。

在主聊天发送 `/evolution`，bot 会创建专属会话和话题，等待主人说明开发需求；发送 `/evolution 开发目标或问题` 则从该目标开始讨论。开发会话记录需求与方案，普通话题中的“同意实施”不会批准开发。bot 先只读检查本项目并提出完整方案；只有方案回复成功送达后，主人在对应话题明确回复“同意实施”或“确认实施”，服务才将任务排入开发队列。方案在后续讨论中变化时，需对最新方案重新明确同意。一次只执行一个开发任务，多个已授权任务依次处理。开发完成、失败或中断只结束本轮实施，原话题仍可继续讨论问题和调整；再次实施前会提出新方案并等待主人重新同意。

后台开发进程先在包含此前未提交改动的脱敏源码副本中实施，再由服务检查并发变化并应用源码改动；真实运行数据和 Git 元数据不进入模型工作区。执行指令禁止 Git add、commit、push 和凭证或运行数据操作，并在结束时检查 Git HEAD 与暂存区未变化。Python 编译检查与完整单元测试在只包含源码的副本中运行，由 `bwrap` 隐藏主人的 home 目录并禁用网络。开发未产出源码改动、编译或测试失败时，执行器把可用的失败说明和受限日志交回同一开发任务，在已批准范围内最多自动修复两轮；开发和修复阶段总时长上限一小时，修复期间不重启服务。验证通过后由服务外进程执行 `./auto_run.sh restart` 并确认监听就绪。重启后的服务在原话题报告结果。每轮开始时把当前源码保存到 `.local/evolution/<会话编号>/runs/<本轮标识>/before/`，并在同一目录生成本轮文件清单与 `report.md`；各次修复的源码快照与摘要保存在该轮的 `attempts/` 和 `attempts.json`。达到修复上限或遇到不可继续的阻碍时，尝试改动保留在 `attempted/`，并尝试把项目源码恢复到本轮开始前状态，服务不重启；新版本启动失败时也尝试恢复并重新启动旧版。恢复结果不确定时明确报告，不覆盖随后发生的人工改动。

开发期间普通消息暂缓处理，`/status` 仍可查看开发状态；已批准、开发中、重启中或通知待送达的开发会话不会被 `/clean` 清理。开发进程意外中断时不自动重跑代码修改，会在原话题报告需核查的状态。开发模型未修改源码时，报告会附上其安全、简短的最终说明；开发过程不保留原始工具输出。此功能使用 `AGENT_BACKEND` 指定的工具，不额外依赖 Codex。完成后不执行 Git commit 或 push；主人可在服务器上审阅并自行提交。

通知草稿按所在话题的 session 隔离：先确定话题归属，再处理确认、取消和补充邮箱；主聊天无 session 的确认不会发送通知。无编号确认只针对本 session 最近已送达的审阅消息，不能通过引用另一话题的草稿批准它。通知结果更新该 session 状态，不进入普通任务历史。

## 群消息监控（bot skill）

在 `.env` 启用 `GROUP_WATCH_SKILL_ENABLED=true` 后，可私聊说“帮我监控 oc_xxx”或“盯一下某群”。群名须能唯一定位；服务会核实主人身份能读取该群，监控从创建后开始，默认持续到取消。主人可指定截止时间、对其他人 @ 自己和自己 @ 自己的不同回复策略；具体策略按任务保存并优先于默认固定回复。每次命中后的私聊提醒默认开启，可在任意私聊话题说“关闭群监控命中提醒”或“恢复群监控命中提醒”，只修改提醒偏好，群自动回复继续；多个监控并存时须指定唯一群名或监控编号。群回复失败仍单独报告异常。同群有临时定制策略时，原默认监控暂停处理该时段的消息，到期后继续，避免重复回复。后台每 `GROUP_WATCH_POLL_SECONDS` 秒检查新消息，不发送周期性的“任务执行中”。`/schedule` 查看生效中监控及最近检查时间；在当前话题直接问“是否还在监控群消息”“监控状态”也会由服务读取同一份记录，列出运行状态、最近检查和异常。超过三个轮询间隔（至少 90 秒）未检查会显示“检查停滞”，不会声称监控正常。复杂追问交给模型时，服务提供相关生效监控的状态快照。主人直接说“停止监控”“可以停止参与活动了”等明确停用语句时，服务核对目标后取消；`/schedule cancel 编号` 也可取消。

群消息结构化 @ 对象与主人 open_id 一致时，服务以主人的飞书用户身份引用回复原消息配置的 `GROUP_WATCH_ACK_TEXT`（默认“收到，我会跟进这条消息。”），末尾添加配置的代发署名，再由 bot 在原私聊任务话题通知主人。默认不创建群话题；只有创建监控时主人明确允许才在话题内回复。文字称呼与其他相关请求只私聊通知，不自动群回复。普通消息和互动卡片正文都参与相关性判断；卡片正文不可读时，日志和监控状态记录消息 ID，供人工核查。姓名和称呼在可选主人资料文件的 `name`、`nickname`、`aliases` 中维护；不同人的同名或含糊提及应以消息上下文判断。监控状态和已处理消息持久保存；群回复或私聊通知结果不确定时不盲目重发。

该功能沿用主人身份的群消息读取权限；自动群回复要求主人拥有用户身份发送权限并仍在目标群。单独要求代发群回复时也使用主人身份；发送失败不会改用 bot 身份。监控使用所选后端对非明确 @ 的消息做相关性判断，定制回复使用同一后端。群消息读取权限或认证失效时，`/schedule` 显示最近错误。

## 定时与条件发送

`schedule-assistant` bot skill 把明确的定时请求整理为任务类型、首次执行时间和周期，服务将其保存到 `.local/messages.sqlite3` 并在到点后通过飞书 bot 发送到原任务话题。一条消息可创建多个独立任务。支持一次、每天和每周的固定文字，以及触发时重新查询 GitLab 的 Issue/MR 待办汇总；时间按 `TIMEZONE` 解释，相对时间以处理请求时的当地当前时间计算；每日和每周按当地日历推进，夏令时变化不会把固定钟点当作固定秒数间隔。可以说“明天 9 点提醒我检查流水线”“每周五 18 点提醒我提交周报”或“每周五 18 点汇总我的 Issue/MR 待办”。其他未接入的实时查询或执行操作，机器人会说明能力边界。

`gitlab-target-watch` bot skill 在启用 `ISSUE_SKILL_ENABLED` 时生效。主人可提供当前 GitLab 主机上的 Issue 或 MR 链接，要求每隔指定分钟检查新评论；未指定时默认 10 分钟。创建时先核实目标并记录请求开始前的评论，不会把旧评论当作新回复，也不会漏掉请求处理期间出现的评论。Issue/MR 普通评论及 MR 代码行讨论回复都会触发，系统记录不会触发。默认首次通知后结束；明确要求持续监控时，在每次发现新评论后通知并继续检查。检查期间静默，查询失败保留任务并在下个周期重试；通知结果不确定时暂停，避免重复发送。

`/schedule` 只列出生效中的提醒、条件通知、群监控和 GitLab 目标监控，话题内只看该话题，主聊天查看全部生效任务；已发送、已取消和发送结果不确定的任务不出现在默认列表。`/schedule 编号` 可查看历史任务状态；`/schedule cancel 编号` 取消生效中的任务。提醒任务的详情包含最近十次执行记录。任务记录没有定期删除机制；清理所属对话时会清空任务正文。任务由服务持久化，重启后继续运行；错过周期时只补当前一次，然后跳到下个周期。发送结果不确定时暂停后续执行，先核查飞书，不自动重发。已排程、监控中或发送结果不确定的任务会阻止所属会话被清理。

发给其他人的通知可绑定一个确定的 GitLab pipeline URL。服务展示完整正文、最终收件人和条件；主人确认后记为 `armed`，每 30 秒查询指定 pipeline，状态为 `success` 时按审阅原文和原收件人自动发送，无需再次确认。`failed`、`canceled`、`skipped` 时不发送，并在原话题报告。若主人对已送达的草稿明确确认正文无误，再追加等待 pipeline 的条件，服务核对正文和收件人完全相同后直接保存条件授权。发送前仍核验主人身份和权限；外部发送结果不确定时停止重发。条件通知也可通过 `/schedule` 查看及取消。

会话数据保存在 `.local/messages.sqlite3`。话题内历史、摘要、保存标记和通知关联按 session 保存。每次只加载本 session 的 `AGENT_HISTORY_TURNS` 轮历史及摘要。任务串行执行，`/status` 保留独立快速通道。

历史检索使用 `.agents/skills/history-search/SKILL.md` 和只读脚本 `scripts/search_history.py`。`/history` 只搜索当前绑定主人的未清理会话，返回命中片段、编号和原话题入口；在原话题发送后续消息即可继续该任务。检索不会在主聊天中切换 session，也不会恢复已清理内容。管理员可在本机运行 `python3 scripts/search_history.py '关键词'` 获取同一范围的 JSON 结果；脚本仅读取数据库，不输出 `.env` 内容。

图片归档的只读索引入口是 `python3 scripts/search_images.py`；默认返回最近 20 张，可用 `--session 编号`、`--message-id om_xxx` 和 `--limit 1..50` 缩小范围。结果包含 `.project/pic/` 中的绝对文件路径、原消息 ID、所属会话与话题入口。bot 在需要查看历史图片时按 `history-search` bot skill 使用该索引，再读取图片本身。图片目录只允许项目用户访问，归档文件不进入 Git；被 `/clean` 确认清理的会话，其归档图片也会删除。

发送使用固定幂等键和持久化分段进度；送达后先保存进度，再核实话题标识。元数据读取失败只重试读取，不重复发送已送达段，也不重新执行模型任务。话题回复失败不会自动退回主聊天；失败记录在 `/status` 和本地日志中。

## 会话保存、清理和运行状态

- `/save`：保护所在话题的会话，主聊天须带编号；`/save 编号`：保护指定会话。保存后 `/session` 列表和详情显示“⭐ 已保存”，所有清理策略都跳过该会话。保护状态重启后保留，覆盖完整历史、摘要及消息关联；磁盘丢失等情况仍依赖数据库备份恢复。
- `/unsave 编号`：取消保存保护，之后可以按清理策略删除。
- `/clean`：查看清理策略；`/clean 1`：预览少于 5 轮的会话；`/clean 2`：预览超过 30 天未使用的会话；`/clean 3`：预览超过 7 天未使用的会话；`/clean 4`：预览所有未保存会话。
- `/clean confirm 清理编号`：确认该批预览，预览须已成功送达，10 分钟内有效。未确认不会删除；重复确认返回原结果。
- `/status`：查看服务运行时长、飞书监听状态、正在处理的任务及排队数量、后端与模型配置、会话数量与保存数量和最近异常。状态来自本地运行记录，未知项明确显示未知；未配置模型时显示 CLI 默认，不猜测具体型号。

一轮按普通用户请求及其对应回答计数，命令和分段回复不增加轮数。清理时间以最后一次实际聊天为准；查看会话和保存不延长清理期限。升级前的会话采用原活跃时间作为初始聊天时间，之后分别记录聊天时间。

清理预览显示待删除数量和最多十个会话的编号、简短标题。确认时只处理这一批，并重新检查保护状态、活跃时间及待处理工作；预览后继续使用或状态变化的会话跳过，新出现的会话不加入。已保存、处理中、仍有待发送/发送失败消息、仍有该话题的队列消息，以及存在未结束通知（draft/sending/uncertain）的会话都会跳过。通知结果不确定时应先核查结果。

清理事务删除会话历史、摘要、消息关联和图片归档索引，并清除队列中该会话已完成消息的正文，仅保留去重 ID 与不含正文的删除标记。对应的归档图片会在事务提交后删除；若删除暂时失败，服务重启后继续清理。对应已结束通知的正文也会清除。清理后保留不含正文的话题删除标记，再进入旧话题会提示开始新任务，不自动恢复历史。引用已清理的消息会说明原会话已清理，不重新下载旧消息来恢复历史。飞书聊天消息、运行日志及已有数据库备份不随 `/clean` 删除；这是应用层清理，不承诺磁盘数据的安全擦除。

这些管理命令及回复不进入普通对话历史、不调用模型、不新建会话。`/status` 使用独立的持久化队列通道，在普通模型调用期间也能回复；其送达仍取决于飞书网络和权限。其他管理命令按原消息顺序处理，避免清理与任务执行互相干扰。删除确认仅识别 `/clean confirm 清理编号`，不会把普通的“同意”用于清理。

## 技能仓库查询与任务使用

在 `.env` 中启用并填写自己的 SSH 技能仓库地址：

```dotenv
SKILLS_REPO_ENABLED=true
SKILLS_REPO_URL=
SKILLS_REPO_BRANCH=
```

启用时 `SKILLS_REPO_URL` 必填，没有内部默认地址；`SKILLS_REPO_BRANCH` 留空使用远端默认分支，填写时只同步该分支。仓库包含 `skills/**/SKILL.md`，文件元数据需要 name 和 description。此功能只额外要求 Git 与仓库 SSH 访问权限，不要求启用 GitLab 或安装其他 AI 工具。修改配置后重启生效。

无论远端仓库名称或分支如何，本地仓库始终为 `.project/skills/`。已有目录必须与配置的 origin、目标分支一致且没有本地修改；不匹配、非快进更新或目录冲突时明确报错，不自动切换分支、删除或覆盖。缓存和 commit 快照保存在 `.local/skills/`，来源或分支变更后不复用不匹配的索引。

首次下载和后续快进均先校验候选内容；校验失败不发布首次检出，也不推进已有工作树或替换正常缓存。该固定目录由技能同步专用，GitLab 仓库准备不会占用或复用它。指定分支不存在时会明确提示，不改用默认分支。

私聊发送 `/skill 需求描述`，先同步仓库，再返回最多 5 个相关技能；只查询，不执行任务。单独 `/skill` 显示用法。同步失败时本次不查找。后台保持每天当地 09:00 同步，首次无快照时立即尝试；09:00 前的手动查询同步不替代当天 09:00 的更新。

普通任务无需先发送 `/skill`：服务按原规则从当前快照选择最多 3 个候选，读取正文与关联资料，交给全局配置的 AI 后端按适用技能处理，并显示本轮实际使用的技能。资料通过只读任务输入提供，相对引用保持可用；技能不会扩大当前工具、网络、目录或业务授权。没有匹配或仓库暂不可用时，按原逻辑继续普通任务并如实说明。`/auto`、群监控和自主开发专用入口不新增这一检索流程。

根级或父级技能不会自动带入其他独立技能子目录；明确引用的关联资料仍可提供。仓库和旧快照须符合共享隔离的受保护路径规则，依赖和缓存目录等限制见[配置说明](docs/configuration.md#技能仓库)；技能材料不可用时继续普通任务。

真实仓库地址、仓库内容和缓存不随源码分享；SSH 认证仍由本机 Git 管理，不在技能中保存凭证。

## GitLab 技能

技能入口为 `.agents/skills/gitlab-assistant/SKILL.md`，每次启用的模型调用都会加载该技能说明。需要安装官方 `glab` 并在运行助手的同一系统用户下登录：

```bash
glab auth login --hostname gitlab.example.com
glab auth status --hostname gitlab.example.com
```

`.env` 配置：

```dotenv
GITLAB_SKILL_ENABLED=true
GLAB_BIN=glab
GITLAB_HOST=gitlab.example.com
```

修改后运行 `./auto_run.sh restart`。应用默认示例关闭 GitLab skill。`GITLAB_HOST` 是提示给模型的默认主机，查询仍需显式确定目标项目；用户给出的项目主机优先。凭证由 glab 管理，不复制 token 到 `.env`、日志或聊天。

仅查询 Issue/MR/流水线通常无需 clone；需要分析源码或修复时，通过 SSH 保存至 `.project/<project>`，不增加主机或命名空间层级。该目录不提交到助手仓库，目标项目内部的 commit/push 按具体用户请求处理。克隆前查找并核对已有仓库的 origin 和工作区，存在同一项目就复用，不重复下载。

三种后端使用相同的任务隔离和受控 GitLab 入口，不向模型开放整个 `.project/` 或 glab 凭证。源码分析使用脱敏副本，修复使用独立工作分支／worktree，保留原 checkout 及已有修改。更复杂诊断可适当提高 `AGENT_TIMEOUT_SECONDS`。

可以在飞书中说：“查看 https://gitlab.example.com/group/project 的未关闭 MR”“分析这条流水线失败原因：<链接>”。在认证成功之前，bot 会提示先登录；不会伪造查询结果。

## 报告创建

`REPORT_SKILL_ENABLED=true` 启用 [report-creation bot skill](.agents/skills/report-creation/SKILL.md)，默认关闭。三种后端的本地报告均独立于 GitLab：未指定格式或类型时生成独立静态 HTML，保存到 `.project/reports/`，完成后通过飞书 IM 在当前任务话题向主人发送文件附件。报告模式允许为当前任务联网和发送附件，不要求开启 GitLab 或线上发布。本地报告工作目录为 `.project/reports/report-<任务编号>/`，厂商沙箱关闭，由共享隔离层落实限制；附件由服务验证并发送，同话题可继续交付已归档报告。

线上报告另外需要 `REPORT_PUBLISH_ENABLED=true`、GitLab 功能以及显式 SSH 目标 `REPORT_PAGES_REPO_URL`（无默认值）；`REPORT_PAGES_BRANCH` 默认 `main`。bot skill 使用本轮服务给出的仓库地址、分支和 `REPORT_REPOSITORY_DIR`，不猜测部署目标。只有当前任务明确要求发布线上报告，才在该目标内提交和 push 本次报告；启用配置本身不授权发布。核实 CI 与 Pages 部署后才报告已上线。

新建通用报告站点可使用 [通用报告模板](templates/self-report/README.md)，包含空目录页、构建器、Pages CI 和测试，不包含历史报告。模板初始化不修改已有配置或部署；实际命名和构建规则以目标仓库为准。

## Issue / MR 处理能力

技能入口为 `.agents/skills/issue-assistant/SKILL.md`。在已有 GitLab 配置基础上设置：

```dotenv
ISSUE_SKILL_ENABLED=true
WORKDAY_MODE=weekdays
ISSUE_SUMMARY_TIME=09:00
ISSUE_WATCH_START_TIME=09:00
ISSUE_WATCH_END_TIME=21:00
ISSUE_WATCH_INTERVAL_SECONDS=600
```

修改后重启服务生效，默认关闭巡检。工作日判断完全在本地完成：`WORKDAY_MODE=weekdays`（默认）只排除周六周日，`everyday` 每天执行，`calendar_file` 使用 `WORKDAY_CALENDAR_FILE` 指定的本地年度 JSON。文件路径相对项目根目录解析，必须包含对应年份和合法、无冲突的 `holidays` / `workdays` 日期数组，数组可以为空，不要求政府来源链接。文件缺失、格式错误或年份不符会明确报错；其他模式不读取该文件。工作日判断不调用模型、不联网。

每日汇总默认当地 09:00 执行一次；巡检默认当地 09:00～21:00，每 600 秒检查新增待办。`ISSUE_WATCH_START_TIME <= ISSUE_SUMMARY_TIME <= ISSUE_WATCH_END_TIME`，时间格式为 `HH:MM`，不支持跨夜；间隔不必为整分钟。汇总时清池并发送全量待办，配置了更早的巡检开始时间时此前只做增量查询。服务恢复后只补当前一次，不追发每个错过的周期；已完成的当天汇总不会因重启再次清池。所有时刻由 `TIMEZONE` 解释。

按配置周期增量巡检中的 Issue 是指派给当前 glab 用户的 open 条目；MR 是该用户为作者或指定 reviewer 的 open 并集，包含 Draft，排除 closed/merged。仅作为 assignee、未指定为 reviewer 的 MR 不纳入。跨所有可访问项目分页获取，任一类别失败不会当作成功的完整列表。

增量提醒中的 Issue 链接后显示 `【创建人姓名创建】`；创建人资料缺失时显示 `【创建者未知】`，不展示“指派给我”这个筛选原因。早间全量提醒和 `/issue` 的指派分组仍展示创建者姓名。

Issue 池以主人绑定会话、GitLab 主机、项目、Issue/MR 类型和编号区分，存于 `.local/messages.sqlite3`。自动通知发送完成后入池；主人提问或与助手讨论的事项也入池。每天配置的工作日汇总时清空一次，旧事项下一工作日会再提醒；同一天仅提醒新增进入待办范围的事项，不因评论更新反复提醒。自动消息发送进度持久保存。

主人发送独立 `/issue`（允许首尾空白和大小写变化）时，任何时间都执行一次手动全量刷新。Issue日报与 `/issue` 共用同一套全量查询、内容生成和刷新池逻辑。两者查询的 Issue 包含指派给我或由我创建的所有 open 条目（包括我创建并指派给他人的 Issue），同一条只展示一次并合并关联原因；MR 范围不变。日报和手动回复都依次展示“我创建的 Issue”“指派给我的 Issue”“我创建的 MR”“需要我审批的 MR”四部分；同时由我创建且指派给我的 Issue 只放入第一部分，同时由我创建且指定我为 reviewer 的 MR 只放入“我创建的 MR”，每部分显示条数（含 0 条）。“需要我审批”按 reviewer 指派识别，不判断是否已点过批准。刷新时：全量查询成功后清空当前池，发送完整待办，成功送达后将本次结果重新入池。查询失败保留原池；发送期间暂停自动巡检，避免重复提醒；旧的未完成自动通知会被本次全量结果替代。带参数的 `/issue ...` 返回用法提示，不创建会话。手动刷新不改变配置的每日汇总或巡检时段。

GitLab Issue/MR 回复末行使用配置的 `MESSAGE_SIGNATURE_TEMPLATE`，仅支持 `{bot_name}`、`{owner_name}`，默认“AI 助手代发”。新通知在审阅前生成完整正文并冻结，配置更新不重写已审阅内容。回复成功后，助手报告结果并询问是否需要飞书通知，默认不发送。主人要求通知时，模型提议内容，服务优先用已确认映射或 GitLab 可见邮箱精确匹配飞书用户。GitLab 邮箱不可见时，按 API 返回的真实姓名搜索同租户飞书用户；只有唯一同名候选，且其邮箱精确复查命中同一账号时，才列为待审阅对象，注明匹配来源和部门，由主人核对。直接要求给某人发飞书消息时，无需先提供邮箱：服务会用姓名搜索同租户通讯录，唯一精确匹配后进入审阅；重名或仅模糊匹配时列出候选人的姓名、邮箱和部门，回复 `选择收件人 通知编号 对象序号 候选序号`。也可回复 `邮箱 通知编号 对象序号 同事邮箱`；只有一个未匹配对象时可直接发送邮箱。收件人未明确之前只展示候选或补充方式，不展示消息正文，也没有可同意发送的草稿。发送前展示最终收件人、正文及“你本人”的发送身份。

通知称呼优先沿用主人在当前任务对话中对收件人的称呼，例如“给小乙发送消息”使用“你好，小乙”，“通知小丙”使用“你好，小丙”。模型将称呼独立填入每位收件人的 `address_as`，真实姓名和邮箱仍用于身份匹配；当前对话没有称呼时，服务使用飞书搜索返回的显示名（有括号时取括号外部分），不额外申请别名读取权限。服务在审阅前为每位收件人保存完整正文，补充邮箱或选择候选人会保留该称呼，修改称呼也需要重新审阅。既有已审阅通知仍按原文发送。

主人审阅后回复 `同意`、`OK` 或 `好的` 即可发送：仅在对应会话只有一条待发草稿，且引用消息或上一条已送达回复为该草稿审阅内容时生效，不要求编号。带 pipeline 条件的草稿在确认后先进入等待状态，条件满足再自动发送。`同意发送 通知编号` 仍兼容，`取消通知 通知编号` 可取消。收件人尚未匹配或未展示全文时不会发送；讨论其他话题后的态度词也不会批准旧草稿。修改正文或对象需要重新审阅，新草稿会替换旧草稿。飞书结果通知末行带相同署名。发送前验证本机登录用户与主人绑定 open_id 一致，所用 app_id 也必须一致。用户身份需要后台开通并本人授权 `contact:user:search`、`im:message`、`im:message.send_as_user`；已有 bot 消息权限不能替代。超时或失败导致发送结果不确定时保存已成功人数，停止自动重发，请主人先核查实际消息。

为某人开通 GitLab 仓库权限而只知道姓名时，助手可先只读搜索飞书通讯录取得邮箱，再到指定 GitLab 主机核实唯一账号、仓库和权限级别。重名时先请主人选人；邮箱或 GitLab 账号无法核实时不执行授权写入。

以下本地诊断不会发送消息，不向池中加入待办：

```bash
python3 scripts/issue_watch.py query
python3 scripts/issue_watch.py workday
python3 scripts/issue_watch.py status
```

`workday` 按配置在本地判断日期；`query` 使用实际 glab 查询。自动巡检保存当日工作日结果。自动巡检和会话可并行；通知审阅与确认由持久化数据控制。

## 本地文件与排查

- `.env`：绑定和启动配置，权限 600，已加入 Git 忽略。
- `.project/`：用于 GitLab 分析的仓库工作区及 `pic/` 图片归档，已加入 Git 忽略。
- `.local/service.log`：运行日志，轮转保留；不记录完整对话或凭证。
- `.local/messages.sqlite3`：待处理消息、回复进度和近期上下文，包含私聊内容。
- `.local/service.json`：PID、进程出生标识及启动时的后端；避免误操作复用 PID 的其他进程。

`.local/` 与 `.env` 都不会提交到 Git。运行日志查看：

```bash
tail -f .local/service.log
```

服务由脚本管理，不会随系统开机自动启动。应用权限、事件订阅及飞书可用范围仍需在飞书后台正确配置。

## 仓库 Pipeline 耗时监控

新增 `/pipeline creat|list|status|start|stop|delete [编号]`，支持独立话题创建确认、失败 Job 原因、排队与执行耗时、完成后的合并告警卡片、重试历史和 GitLab Pages 长期筛选报告。

开发和审查期间 `PIPELINE_MONITOR_ENABLED`、`PIPELINE_PUBLISH_ENABLED` 默认关闭。前者启用采集和通知，后者独立控制后台 Git 提交与 push。既有 `.env` 不自动修改；审查、配置及服务重启后生效。

报告发布目标没有内部默认值。关闭发布时可不配置目标，正常采集与投递卡片；开启发布须先开启监控，并填写显式 SSH 目标：

```dotenv
PIPELINE_PAGES_REPO_URL=git@gitlab.example.com:team/monitor-site.git
PIPELINE_PAGES_BRANCH=main
```

仓库地址只接受 SSH；报告 API 主机和项目由地址推导，本地工作区为 `.project/<仓库名>/`。工作区须事先克隆并核对 origin，发布器不会自动克隆或覆盖远端。分支、Runner 和 Pages 权限由部署者配置；启用发布不绕过站点源码变更审查。已有发布记录绑定目标身份，切换目标不会自动迁移历史。

新建站点可使用 [流水线报告模板](templates/pipeline-pages/README.md)，其中不含真实任务数据。统计、报告日期与卡片展示按 `TIMEZONE`，站点 manifest 含 `timezone`；无该字段的旧数据兼容 `Asia/Shanghai`。统计口径、发布快照与审批见 [Pipeline 监控说明](docs/pipeline-monitor.md)。
